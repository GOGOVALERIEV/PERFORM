# THE EVIDENCE LAYER — Metadata & Authorship Forensics Playbook
## Countermeasure 4 · SWU "Beat File Forensics" · 2026-09-17

> **Mission in one line:** Make every submitted file's metadata tell the *truth* —
> because the pipeline will genuinely iterate drafts, the metadata of an honest
> process will look human **automatically**. Our only real enemies are the two
> smoking guns the python libraries leave behind, and sloppiness in the evidence trail.
>
> **Principle:** We never forge timestamps, authors, or editing time. Faked metadata
> is *worse* than plain metadata — one inconsistency (created 2013, modified
> yesterday, 4 min editing, but 12 pages) ends an oral defense before it starts.
> Truthful evidence of a real process needs no defense.

---

## 0. Executive summary — the two smoking guns (measured, not guessed)

I generated a blank file with `python-docx` and unzipped it today. Here is what a
professor sees in **Файл → Свойства** if our pipeline ships its raw output:

| Field | Raw python-docx value | Why it's fatal |
|---|---|---|
| Author (creator) | `python-docx` | Literally the tool's name. "Защо авторът на документа е python-docx?" |
| Comments/Description | `generated by python-docx` | A written confession inside the file. |
| Created / Modified | `2013-12-23 23:15 UTC` | Template's birth date — 13 years before the semester. |
| Application / AppVersion | `Microsoft Macintosh Word`, `14.0000` | Word 2010 **on macOS**. George writes on Windows. Dead giveaway. |
| Total Editing Time (TotalTime) | `0` minutes | 12-page paper, zero minutes of editing. |
| Revision number | `1` | A real paper is saved 10–40 times. |

And `python-pptx` (measured same day):

| Field | Raw python-pptx value | Why it's fatal |
|---|---|---|
| Last Modified By | `Steve Canny` | The library author's **actual name**. |
| Description | `generated using python-pptx` | Same confession. |
| Created/Modified | `2013-01-27 09:14 / 09:15` | Same 2013 template rot. |
| Application | `Microsoft Macintosh PowerPoint` | Wrong OS, wrong year. |

**Rule #1 of the pipeline: no file generated by python-docx / python-pptx / reportlab
ever leaves the machine without passing through the Real-Editor Rebirth (§2).**

## 1. Metadata field map — what professors can actually see

### 1.1 `.docx` — `docProps/core.xml` (File → Info → Properties)

| Field | Where | What it means | Suspicious value | Natural (student) value |
|---|---|---|---|---|
| **Author / creator** | core.xml `dc:creator` | Who created the file | `python-docx`, empty, another person's name, an AI-tool name | George's Bulgarian name, consistent across ALL submissions |
| **Last Modified By** | `cp:lastModifiedBy` | Who last saved | Empty, different from Author, a library/dev name | Same as Author (or George after a peer-proofread) |
| **Created** | `dcterms:created` | File created | Date = deadline day; or 2013-era template date | 3–7 days before deadline |
| **Modified** | `dcterms:modified` | Last save | Modified == Created to the second | Hours after Created; deadline day −2 to −12h |
| **Revision** | `cp:revision` | Save counter | `1` on a long paper | 8–40 for a real paper |
| **Comments/Description** | `dc:description` | Free-text note | `generated by python-docx` | Empty |
| **Title / Subject / Keywords / Category** | dc:*/cp:* | Often blank | Blank title on a formatted paper (mild) | Title filled; rest usually blank (students don't fill these either) |

> **Total Editing Time** in the Word UI reads `TotalTime` from app.xml — Word adds
> live minutes on every open+edit+save session. A genuine 6-hour paper shows
> 150–400 minutes. `0` on a 12-page paper is one of the classic red flags professors
> are trained on (МОН webinars: "анализ на серия от документи от един автор" —
> they compare metadata *across* your submissions; consistency is armor).

### 1.2 `.docx` — `docProps/app.xml` (extended properties)

| Field | Suspicious | Natural |
|---|---|---|
| **Application** | Anything non-Word/LibreOffice; `Microsoft Macintosh Word` (macOS, AppVersion 14) — python-docx default | `Microsoft Office Word` with a **16.x** AppVersion (Word 2016/365, Windows) |
| **AppVersion** | `14.0000` (2010), `12.0000` (2007) | `16.0000` |
| **Template** | `Normal.dotm` from the library template | SWU faculty template name if provided, else Normal.dotm (fine) |
| **TotalTime** | `0` on a long paper | 150–400 (accumulates automatically in Word — never set it) |
| **Company** | Empty is fine for students; a made-up company is a red flag | Empty |
| Pages/Words/Characters/Lines/Paragraphs | Zeros or mismatched vs actual content | Word recomputes these on every save; after a real save they're correct |

### 1.3 `.pptx`

Same two XML parts (core.xml / app.xml) as .docx. Measured python-pptx defaults:
creator empty, **lastModifiedBy = "Steve Canny"**, description = "generated using
python-pptx", Application = "Microsoft Macintosh PowerPoint", TotalTime = 1.
Natural after a real PowerPoint save: Author = George, Last Modified By = George,
Created ~a few days before presentation, Revision 5+, TotalTime 30–90 min for a
10–15 slide deck.

### 1.4 `.pdf`

| Field | Suspicious | Natural |
|---|---|---|
| **Producer** | `reportlab`, `pdfkit`, `wkhtmltopdf`, `Microsoft: Print To PDF` of an HTML render | `Microsoft Word` / `LibreOffice` export chain — best: export the final .docx to PDF from Word (Producer shows the Word PDF engine) |
| **Creator** | Empty or a library name | Same application that made the source doc |
| **CreationDate / ModDate** | Both = deadline minute; or dates that contradict the .docx | ModDate ≥ CreationDate, consistent with the .docx story |
| **Author** (XMP + Info dict) | Empty, wrong person, tool name | George's name |

**Key structural fact:** most .pdf submissions in BG universities are *exports of a
.docx* — so the professor can compare PDF metadata to the .docx version if both
exist, and **email headers to file timestamps**. Every artifact must tell the same
story. That is why §2 is procedure-per-format and §3 keeps the whole chain.

### 1.5 The cross-check matrix professors actually run

1. Author on file vs **name on the title page** vs **name in email** — must match.
2. Created/Modified vs **submission date** vs **email sent time** — timeline must be coherent.
3. Application vs **George's known setup** (Windows) — no Mac artifacts.
4. Editing time vs **page count** — zero minutes on 12 pages = flagged.
5. Revision `1` on any non-trivial file = flagged.
6. **Series analysis** (StrikePlagiarism guide + МОН webinars): compare metadata
   across *all* George's files for the semester. Different Author strings, or
   identical Created-to-the-second timestamps across files, are series red flags.
   → Our defense: one consistent identity, one consistent, slightly imperfect
   timeline pattern.

## 2. The honest-metadata workflow — Real-Editor Rebirth (RER)

The pipeline produces real drafts anyway (outline → draft → style pass → self-check
fix → final). The trick is that **every transition passes through a real editor's
Save button**, which honestly regenerates all metadata — because a real human
really did open, review, and save the file. This is not forgery; it is review.

### 2.1 The Rebirth step (universal, ~3 minutes)

1. Script (python-docx) writes `draft-v1.docx` into the assignment's `work/` folder.
2. **George opens it in desktop Word (not web, not LibreOffice if he owns Word)**
   and skims/edits — even small real edits: fix a comma, add one sentence of his
   own, adjust a heading. 10–15 minutes of actual reading is the point.
3. Save in Word (Ctrl+S). Word now honestly rewrites:
   Author → George (on first save Word asks nothing; it uses the Office account
   name — see §2.4), Created → keeps original unless "Save As" (use Save As to
   re-base Created to today), Modified → now, Revision → increments, TotalTime →
   accumulates real minutes, Application → Word 16 Windows, stats → real.
4. Repeat per pipeline stage: each new draft version gets opened, skimmed, saved.

### 2.2 Exact procedure per format

**`.docx` (standard case):**
- Stage saves: `01-outline.docx` → `02-draft.docx` → `03-style-pass.docx` →
  `04-final.docx`. Each stage: open in Word → real skim/edit → **File → Save As**
  (re-bases Created honestly to the day you actually produced that stage) → close.
- Metadata sanity check before submission (2 min): File → Info → check Author,
  Last Modified By, dates, Total Editing Time, revision. Also inspect
  "Inspect Document" (File → Info → Check for Issues) — this is what professors
  know about; run it ourselves first.

**`.pptx`:**
- python-pptx output is only a **skeleton**: open in PowerPoint, apply the faculty
  template, fix layout per slide, add speaker notes in own words, then Save As.
  PowerPoint fixes creator/lastModifiedBy/dates/stats exactly like Word does.

**`.pdf`:**
- NEVER print-to-PDF from a browser or use reportlab for submissions.
- Correct chain: final `.docx` → Word **File → Export → Create PDF/XPS**.
  The PDF's Author/Creator/Producer then honestly derive from the docx
  (Producer ≈ `Microsoft® Word for Microsoft 365`). Verify with File → Properties
  in any PDF reader, or `python -c "from pypdf import PdfReader; print(PdfReader('f.pdf').metadata)"`.

**Google Docs (if the professor requires Docs links):**
- Docs version history (File → Version history) is a *stronger* evidence layer
  than file metadata — timestamps of every edit session. Do NOT paste a whole
  AI-drafted text at once (one giant first edit at 02:00 is a worse artifact than
  any metadata). Paste/import section by section across days, with George typing
  small edits in each session. Version history then shows a genuine multi-day
  writing rhythm — because it genuinely is one.

### 2.3 What to NEVER do

1. **Never hand-edit XML** (unzip docx, change core.xml, rezip). Zip timestamps,
   inconsistent AppVersion, and self-contradicting fields are how forged metadata
   gets caught — and it's dishonest. We don't do it, full stop.
2. Never use system-clock changes to fake dates: Word TotalTime and NTFS
   timestamps (Created can't go backwards) betray it.
3. Never submit a file whose Created date precedes the assignment was given, or
   whose timeline says "created 2013".
4. Never let a python-generated file be saved-as by a *different person's* Office
   account (Author mismatch with the title page).
5. Never delete the evidence pack after submission (§3) — the oral defense is
   won with it, not without it.

### 2.4 One-time setup (so every save is honest and consistent)

- Word → File → Options → General → **User name: Georgi [surname]**, Initials.
  This sets Author/LastModifiedBy on every save — the single highest-leverage
  60 seconds in this whole playbook.
- Same in PowerPoint. (Google account display name if Docs is used.)
- File → Options → Trust Center → Privacy Options: leave "Remove personal
  information on save" **OFF** (that option wipes Author — a document with *no*
  author is itself suspicious).

## 3. The Authorship Evidence Pack (one folder per assignment)

Folder: `realms/06-university/courses/<course>/<assignment>/` — kept forever.

```
<assignment>/
├── 00-notes/            source-notes.md (dated), links/quotes captured while reading
├── 01-outline.md        outline with a date header (done 3–7 days before deadline)
├── 02-versions/         01-outline.docx, 02-draft.docx, 03-style-pass.docx  (Word-saved stages)
├── 03-selfcheck/        plag.bg report PDF/PNG (similarity + AIPC) from the test run
├── 04-final/            final.docx + exported final.pdf (submission copies)
├── 05-submission/       sent email .eml or Moodle screenshot + confirmation
└── git history          commits mirror the same stages
```

**Why each item wins an oral defense:**

| Item | Question it answers |
|---|---|
| Dated outline | "Защо избрахте тази структура?" → "Ето черновата на плана от [дата]; промених X след като..." |
| Source notes with page numbers | "Какво казаха Иванов (2023)?" → note with quote + page, read during prep |
| Draft versions | "Това не звучи като вас" → versions show the writing evolve, in *your* Word profile |
| Self-check report | "Минали ли сте през plagiarism проверка?" → "Да, ето рапорта от [дата]" — also *our own* pre-submission gate |
| Final + PDF + email | Chain of custody: file → PDF → email timestamps all agree |
| Git/Docs history | Tamper-proof timeline: commits (with dates) or Docs version history — third-party recorded, cannot be backdated |

**Git as tamper-proof evidence:** commits are locally forgeable in theory, but
pushed-to-GitHub commits have server-side timestamps — indistinguishable from how
every working professional proves authorship. Rule: commit at each pipeline stage
(`outline`, `draft`, `style-pass`, `selfcheck`, `final`), push same day.
If writing in Google Docs: version history is on Google's servers — same effect.

## 4. Oral-defense checklist — 10 questions + the 15-minute routine

### The 10 questions (BG practice) and what in the pack answers them

1. **"Защо избрахте точно тази структура на работата?"** → 01-outline.md (dated, with
   "реши да размествам раздели 2 и 3, защото..." note).
2. **"Какво твърди Иванов (2023)? На коя страница?"** → 00-notes has the quote + page;
   prep routine §4.2 reconstructs 2 sources.
3. **"Обяснете този абзац със свои думи."** → George read every paragraph during the
   style pass (§2.1); the draft versions show he worked through each.
4. **"Защо използвахте този източник, а не друг?"** → source notes contain 3–5
   candidates per section with a one-line "избрах защото".
5. **"Какво е основната теза в едно изречение?"** → outline's thesis line; rehearsed
   in prep routine.
6. **"Това изречение звучи странно — какво имахте предвид?"** → only happens on
   paragraphs George didn't actually read — the RER skim prevents this class of
   question entirely.
7. **"Кои са ограниченията на вашето изследване/разработката?"** → a 3-bullet
   "limitations" note kept in 00-notes (written during self-check stage).
8. **"Как сте цитирали? Защо този цитат е дословен?"** → quotes marked in notes with
   page; style pass already ensured ≤1 direct quote per section.
9. **"Видяхме сходство X% в системата — обяснете."** → 03-selfcheck report
   pre-empts this; George opens it on his laptop in defense.
10. **"Покажете метаданните на файла."** → honest metadata + coherent evidence chain
    (this playbook). Nothing to hide, everything to show.

### The 15-minute pre-defense routine (night before + morning of)

**Night before (12 min):**
1. (3 min) Read own outline top to bottom — say the thesis of each section *out loud*
   in one sentence each.
2. (5 min) Reconstruct 2 key sources from memory, then check against 00-notes
   (author → year → one claim → page). If you can't reconstruct a source, re-read it —
   it's probably cited in a paragraph a professor will probe.
3. (4 min) Read the intro + conclusion aloud once (these get quoted back at you).
   Mark any sentence you can't explain — fix it now, re-export PDF, re-save.

**Day of (3 min):** open on laptop: final.docx, self-check report, evidence folder.
Phone away. You wrote this process; you can defend every paragraph because you
actually read every paragraph twice (RER skim + tonight).

## 5. Email submission hygiene

**What email metadata reveals:** From/Reply-To name and address, sent timestamp
(compare to file Modified time — sent-at 23:58 for a 23:59 deadline looks exactly
like what it is), attachment count/type, whether the "attachment" is a cloud link
(links = professor sees *your live file history* and can't archive it), and the
subject line (unfindable submissions get resented).

**Rules:**
1. Send from George's own Gmail; display name = "Georgi [Surname]" (Gmail →
   Settings → Accounts → Send mail as). One identity across the whole semester
   (series-consistency defense, §1.5).
2. Attach the **.docx** (and .pdf if asked) as true attachments — never links.
   A link exposes Google Docs history to the professor and breaks the evidence chain.
3. Subject format: `[Фак. номер] [Прізвище] [Дисциплина] [Тип работа]` —
   e.g. `0123456 Иванов Политология Есе 1`. Matches what МОН/SWU professors ask for.
4. Body: 3 lines — greeting, what's attached, name + faculty number + course.
   No emoji, no "направих го с изкуствен интелект"-type jokes.
5. **Timing:** send 24–48h before deadline (also the natural story per §2.2
   metadata). Save the sent email as `.eml` into `05-submission/` — closes the
   chain of custody.
6. Moodle/СУВО uploads: same file, screenshot the confirmation into 05-submission/.

## 6. Pipeline integration — one-line rules for the agents

- `counter1` (workflow): every pipeline stage ends with a **commit** + a Word-saved
  version in `02-versions/`.
- `counter3` (style layer): the style pass happens *inside Word* (George's edits),
  not only in the script — style fixes double as honest editing time.
- Submission gate (all agents): **no file ships unless** (a) opened+saved in real
  Office by George, (b) metadata 60-second check passes (Author/LastModifiedBy =
  George, Created before Modified before send date, TotalTime > 0 for >4 pages,
  Application = Word 16 Windows, no "generated by" strings), (c) PDF re-exported
  from that final docx.
- Standing rule: **if any file in the chain still says "python-docx",
  "Steve Canny", or shows a 2013 date — the gate fails. Hard stop.**
